# Email — architecture, deliverability and runbook

Last audited 2026-09-27. Statements about the provider are marked **verified**
(read from the Resend API that day) or **unverified** (could not be checked
from the audit environment). Nothing here says a DNS record exists unless it
was seen.

## Two senders, one domain

| Mail | Sent by | Transport | Templates |
|---|---|---|---|
| Sign-up confirmation, password reset, email change, reauthentication, magic link | Supabase Auth (GoTrue) | SMTP → `smtp.resend.com:587`, user `resend`, password = Resend API key | `supabase/templates/*.html`, generated by `pnpm auth:templates`, pasted into Supabase → Authentication → Emails |
| Everything else (19 product events + 4 digests) | This app | Resend REST API (`src/lib/email/send.ts`) | Block components in `src/lib/email/components.ts`, copy in `copy.ts` |

Both send as `Brokers Connect <noreply@brokersconnect.net>`, so both align with
the same SPF/DKIM for DMARC.

## The app's pipeline

```
product action ──after()──▶ notify.ts ─▶ envelope.ts ─▶ service.deliver() ─▶ send.ts ─▶ Resend
 (server action / cron)      one fn per    header/body/     claim → send →     one POST
                             event         CTA/footer       record
                                                              │
                                  email_log (outbox) ◀────────┘
                                       ▲        ▲
              /api/cron/email-retry ───┘        └─── /api/email/webhook ◀── Resend events
              (hourly, re-derives from entity)       (signed, svix)
```

- **Only `deliver()` sends.** Nothing else imports `send.ts`. Components and
  actions call `notify*()` functions; those choose blocks and a recipient and
  never write HTML.
- **Typed templates.** `src/lib/email/templates.ts` names every template and
  its category. `deliver()` only accepts those names, and refuses a message
  whose unsubscribe does not match its category.
- **Outbox first.** `claim_email()` writes the `email_log` row *before* the
  send, keyed on a `dedupe_key`. A duplicate event, a double-click or a re-run
  cron loses the unique insert and sends nothing.
- **The business action never depends on mail.** Every `notify*()` runs in
  `after()`, returns instead of throwing, and a provider outage leaves a
  `failed` row for the sweeper — the application, listing or decision is
  already committed.
- **No message bodies are stored.** Retries re-derive the message from the
  entity it was about (`rebuild.ts`).

### Categories

| Category | Unsubscribe | Preference | Complaint-suppressed | Hourly ceiling |
|---|---|---|---|---|
| `security` — password changed, visibility changed, account approved/rejected | never | never | **no** | exempt |
| `transactional` — welcome, receipts, withdrawal, job submitted, company verification, profile ready | never | never | yes | 30/h |
| `preference` — new applicant, applicant digest, status changes, moderation result, expiry, saved-search/follow digests, profile nudge | RFC 8058 one-click | `notify_applications` / `notify_status` / `notify_digest` / `notify_profile_nudge` | yes | 30/h |

Turning off a marketing-style stream (`notify_digest`) cannot stop a security
notice: security templates carry no unsubscribe and check no preference.

Every preference email carries two ways out (`unsubscribeLinks`): the footer
link opens `/unsubscribe`, which asks before it changes anything, so a link
scanner cannot unsubscribe anybody; the `List-Unsubscribe` header names
`/api/unsubscribe`, which a mail client's own button POSTs
`List-Unsubscribe=One-Click` to and which makes the change there and then.
(Until 2026-10-01 the header named the page, which answers a POST by rendering
itself: a 200, and nobody unsubscribed.)

The profile nudge is opt-in: `notify_profile_nudge` is off unless the person
turns it on (migration 337), because it answers nothing they asked for. It
used to ride on `notify_digest`, which is on by default and labelled as the
weekly roundup. `email_log` rows, recipient included, are pruned after 180
days; a provider's failure reason is stored with any address removed.

Deliberately **not** sent: a CV, phone number or WhatsApp number in any email
(the button leads to the authenticated page); an invitation to a colleague
without an account (the team form adds existing accounts only); open/click
tracking.

Every template can be previewed without sending at `/api/email/preview`
(admin-only in production), in Arabic and English, at 600px and 375px.

## Arabic, RTL, mobile

`renderEmail()` sets `lang`/`dir` on the document and on every block cell,
aligns per direction, uses a single 600px fluid column with no fixed-width
tables, and Western digits in both locales. User-typed text (job titles,
names, notes) is HTML-escaped and URLs pass `safeHref()` (https/mailto only).
Latin fragments inside Arabic copy stay in their own direction because each
block carries `dir`. Auth templates are Arabic only (Supabase stores one
template per type).

## Retries

- Send path classifies failures: 408/429/5xx/network → retryable; other 4xx
  → attempts exhausted immediately.
- `/api/cron/email-retry` (hourly at :17) takes up to 25 rows that are
  `queued`/`failed`, under 3 attempts, older than 5 minutes and younger than 3
  days. It releases the old row's key and re-runs the event's `notify*()`,
  which claims a fresh row. Digests and point-in-time notices are not retried
  (see `rebuild.ts` for why).
- An unconfigured provider or a refused test sender leaves rows `queued`
  without spending attempts, so they go out once configuration is fixed.
- Delivery is at-least-once in one narrow window: if the process dies after
  Resend accepted a message but before the row was marked `sent`, the sweeper
  resends it.

## Bounces, complaints and delivery state

`/api/email/webhook` verifies the Svix signature (5-minute replay window,
timing-safe, rotation-aware), then calls `record_email_event()`, which in one
statement:

1. records the event id — a replayed event is a no-op;
2. matches the message by Resend id **in our outbox only** — events about
   another site's mail on the shared Resend account change nothing;
3. moves the status forward only: `queued < sent < failed/delivered <
   bounced/suppressed < complained`;
4. suppresses the **recorded** recipient:

| Resend event | Status | Suppression |
|---|---|---|
| `email.delivered` | delivered | — |
| `email.delivery_delayed` | (sent, if still queued) | — |
| `email.bounced`, `bounce.type` Permanent/Undetermined/absent | bounced | `hard_bounce` — blocks everything |
| `email.bounced`, `bounce.type` Transient | bounced | third in 30 days → `repeated_soft_bounce` |
| `email.complained` | complained | `complaint` — blocks all but security |
| `email.suppressed` | suppressed | `provider` — blocks everything |
| `email.failed` | failed, not retried | — |

Reserved domains (`.test`, `.invalid`, `example.com`…) are never attempted.
Admins see all of this at `/admin/email`.

## Spam and abuse controls

| Trigger | Limit | Where |
|---|---|---|
| Password reset | 3/h per address, 20/h per IP; same answer whether or not the account exists | `requestPasswordReset` (server action) + GoTrue |
| Confirmation resend | 3/h per address, 20/h per IP | `resendConfirmation` (server action) + GoTrue |
| Any Auth email to one address | 1 per 60 s | GoTrue `max_frequency` |
| Auth email project-wide | 60/h | GoTrue `rate_limit.email_sent` |
| Add team member (email lookup) | 20/h per user | `addCompanyMember` |
| Password-changed notice | 5/h per user, and only if the password really changed in the last 5 min | `announcePasswordChange` |
| Applications / reports | 30/day, 10/day per account | triggers (migration 19) |
| Any non-security mail to one address | 30/h | `claim_email` |

No endpoint accepts a free-form recipient, subject or body. Every recipient is
resolved server-side from a user id through the service role, so the platform
cannot be used as a relay.

## Links and tokens

- Auth links are GoTrue's single-use tokens, 1 hour (`otp_expiry = 3600`),
  PKCE code exchange at `/auth/callback`.
- `next`/redirect targets go through `safeNext()` (same-origin paths only;
  `//`, `\`, schemes, control characters and their percent-encoded forms are
  refused). The resend action only ever redirects to `/auth/callback` on the
  site's own origin.
- Unsubscribe links carry a random per-user token (not the user id), act only
  on POST (so scanners prefetching GET do nothing), and can only switch a
  preference off.
- The reset and resend forms never reveal whether an address is registered.
  Known residual: the email-change form tells a *signed-in* user that an
  address is taken (GoTrue's own error), behind GoTrue's rate limits.

## Tests

`pnpm test:email` (in-process Postgres, real migrations) covers escaping,
safe hrefs, signature verification and replay window, preview coverage,
template registry coverage, idempotent claims, suppression, reserved domains,
retry budget and permanent failures, delivered-only-from-webhook, replayed
events, out-of-order events, foreign events on the shared account, hard/soft
bounce handling, provider suppression, provider failure, complaint vs security
mail, the per-recipient ceiling, the rate limiter, test-sender refusal, RLS
closure of every email table, and that every link in every template resolves
to a real page. `pnpm test:auth` covers the confirmation landing and the
reset/resend flows' wiring.

Manual checks that need a real inbox (not run in the audit): send each
template to Gmail, Outlook and Apple Mail on a phone via
`/api/email/preview`-verified content; confirm `List-Unsubscribe` renders on a
preference message and not on a security one; confirm an expired reset link
lands on the "link expired" message.
